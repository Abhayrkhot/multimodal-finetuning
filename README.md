# multimodal-finetuning

LoRA fine-tuning of a CLIP-based vision language model, **LLaVA-1.5-7B** (CLIP ViT-L/14-336
image encoder, 2-layer MLP projection, Vicuna-7B decoder), on **Visual7W** 4-way multiple-choice
visual question answering. The pipeline covers data, training, evaluation by question type,
calibration, quantized inference on an A100, and a small HTTP service. Adapters (LoRA) are written
directly in PyTorch.

Every number in the tables below is generated by `scripts/gen_readme.py` from the per-question
predictions and run records committed under [`results/explorer`](results/explorer); CI fails if
the README and the data disagree.

## Controls

<!-- BEGIN controls -->
- **Harness check.** Zero-shot ScienceQA-IMG accuracy is 68.8% with this prompt, image padding and letter scoring; the LLaVA-1.5 paper reports 66.8% for the same model (it parses generated text, while this harness compares the option letters' logits directly).
- **The image matters.** With every image replaced by a blank one, zero-shot accuracy falls from 80.6% to 43.1% (chance is 25%): Visual7W's distractors leave some text-only signal, which is why the blank-image row is reported per type.
- **No answer-position shortcut.** Correct answers are uniform over A-D by construction; the fine-tuned model predicts A 25.2%, B 25.1%, C 24.9%, D 24.8%.
- **Merging is lossless.** The merged BF16 checkpoint scores 87.02% vs 87.02% with separate adapters (+0.00 pts).
<!-- END controls -->

## How it works

```
image ──► CLIP ViT-L/14-336 ──► 576 patch features ──► MLP projector ──► 576 image tokens ─┐
          frozen 304M + LoRA r=16 in the        (trained, 21M)                             │
          23 layers LLaVA reads (6.8M)                                                     ▼
prompt ──► "USER: <image>\n{question}\nA. ..\nB. ..\nC. ..\nD. ..\n           Vicuna-7B, frozen + LoRA r=16
            Answer with the option's letter ... ASSISTANT:" ───────────────► on q,k,v,o,gate,up,down (40M)
                                                                                          │
                                                       next-token logits of "A" "B" "C" "D" ─► softmax
```

- **Task and split.** Visual7W "telling": 139,868 questions on 28,653 COCO images, each with one
  correct answer and three human-written distractors, split by image (no image appears in two
  splits). The answer's position is shuffled with a per-question seed, so it is uniform over A-D
  and identical in every run. Two questions whose options repeat after normalisation are dropped.
- **Why this model and dataset.** LLaVA-1.5's training mix is published (LLaVA-665K: VQAv2, GQA,
  OK-VQA, A-OKVQA, OCR-VQA, TextCaps, RefCOCO, VG regions, ShareGPT), and Visual7W is not in it, so
  zero-shot and fine-tuned numbers are measured on a genuinely held-out task. The vision encoder
  is CLIP, and the projector + decoder layout is the standard image-encoder/projection/decoder VLM.
- **Scoring.** One forward pass per question; the prediction is the argmax of the option letters'
  next-token logits, and their softmax is the confidence used for calibration. Batches are
  left-padded with explicit position ids, so only the last position's logits are computed
  (`logits_to_keep`), and a test checks that padding never changes a score.
- **Adapters** ([`mmft/lora.py`](mmft/lora.py)). LoRA is implemented from scratch: Kaiming-uniform A,
  zero B (a wrapped model starts identical to the base), fp32 adapter weights on a bf16 base under
  autocast, and an exact merge into the base weights for deployment. The projector is trained in
  fp32 at a 10x lower learning rate than the adapters. Optionally the CLIP encoder gets adapters
  too, only in the 23 layers whose output LLaVA uses (it reads the penultimate layer, so the last
  one would get no gradient).
- **Recipe selection.** Candidate recipes (decoder adapters only vs. decoder + CLIP adapters, one
  vs. two epochs) are compared on 5,000 validation questions and the best one is reported; test
  is never used for a choice. A fourth run (CLIP adapters, two epochs) was stopped early once the
  two-epoch schedule showed no gain on validation.
- **Training** ([`mmft/train.py`](mmft/train.py)). Plain PyTorch: AdamW, cosine schedule with
  warmup, gradient checkpointing, loss on the answer letter and end-of-turn token only.
- **Calibration.** Expected calibration error (15 equal-width bins), NLL and Brier score, before
  and after temperature scaling, with the temperature fitted on 5,000 validation questions and
  applied to test.
- **Quantization.** bitsandbytes LLM.int8 and NF4 (double quantization, bf16 compute) applied to
  the language model; CLIP, the projector and the LM head stay bf16. Each precision is measured in
  a fresh process.

## Reproduce

Runs were on Northeastern's Explorer cluster (Slurm, one GPU per job); any CUDA GPU with 40 GB+
works. Tests and lint run on a CPU.

```bash
pip install torch==2.14.1 --index-url https://download.pytorch.org/whl/cu126
pip install -r requirements.txt bitsandbytes==0.50.2
python -m mmft.cli data v7w --root data/visual7w        # 1.9 GB from Stanford, sha256-checked
python -m mmft.cli data sqa --root data/sqa             # ScienceQA-IMG test (harness check)
bash scripts/stage_baseline.sh                          # zero-shot, blank-image control, ScienceQA
bash scripts/stage_train.sh                             # train, evaluate (val, test, ScienceQA)
bash scripts/stage_merge.sh v7w_r16_vis                 # fold the selected run's adapters into the weights
bash scripts/stage_bench.sh v7w_r16_vis                 # bf16 / int8 / nf4 memory and latency, serving
bash scripts/stage_quant_acc.sh v7w_r16_vis             # test accuracy at each precision
python scripts/gen_readme.py                            # rebuild the tables above
```

On Slurm: `sbatch slurm/setup.sbatch`, then `sbatch slurm/gpu.sbatch scripts/stage_train.sh`
(the GPU job runs the test suite before the stage).

## Serve

```bash
python -m mmft.cli serve --model runs/v7w_r16_merged --quant nf4 --temperature <T from val>
curl -s localhost:8000/v1/answer -H 'content-type: application/json' \
  -d '{"image_b64": "'"$(base64 < photo.jpg)"'", "question": "Where is he sitting?",
       "choices": ["At a park.", "On a bench.", "On the grass.", "At a dining table."]}'
```

The response carries the chosen option, its temperature-scaled confidence, all option
probabilities, and an `abstain` flag when confidence is below `--abstain-below`.

| `results/explorer/` | per-question predictions (`*.jsonl.gz`), run records, benchmarks |
| `tests/` | CPU tests on a tiny random LLaVA with the real processor |

## Limitations

- One training seed per schedule, so there are no across-seed error bars; the test set is large
  enough that the sampling interval on accuracy is about ±0.3 points (shown in the results table).
- Visual7W's human-written distractors leave some signal in the text alone (see the blank-image
  control), so accuracy is not purely visual.
- LLaVA-1.5 (2023) was chosen because its training data is published, which makes the held-out
  claim checkable; the code loads any Hugging Face `LlavaForConditionalGeneration` checkpoint.
- The inference benchmark times one scoring forward pass (the deployed workload), not
  autoregressive generation. bitsandbytes LLM.int8 is slow because of its outlier decomposition;
  NF4 is the precision that saves memory without giving up throughput.
- The HTTP service runs one forward pass at a time; there is no request batching.
